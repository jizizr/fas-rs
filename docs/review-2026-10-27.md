## CI 失败与修复

原始失败：[run 40513052191](https://github.com/jizizr/fas-rs/actions/runs/40513052191)。

1. 自动抓取 latest 得到了 NDK r30。cargo-ndk 4.1.2 给 bindgen 配置了 sysroot，却没有 API 后缀；bindgen 从 Rust target 推导出的 `aarch64-linux-android` 触发 `Unversioned target triples are not supported`。同时宿主 libclang 与 NDK 头文件版本不匹配。
2. xtask 只等待子进程，不检查退出状态，继续复制不存在的二进制并 panic；如果旧产物仍存在，还有误打包的可能。
3. 后续完整构建发现 frame-analyzer 的 build.rs 每次都编译最新版 bpf-linker，并忽略子进程失败。当前新版 linker 需要额外 LLVM 环境。

本次给 bindgen 显式传入 `aarch64-linux-android31`，使用 NDK 自带 libclang；固定 NDK/cargo-ndk/pnpm/BPF linker，校验预编译 linker 的 SHA-256，并检查全部 xtask 子进程退出状态。WebUI 使用现有 pnpm 锁文件；frame-analyzer 保留 0.3.4 运行时代码，纳入本地维护并修正构建脚本。Rust nightly 本身仍是滚动版本。

## Android 17：已落地的兼容改动

- **新 Surface 签名回退**：AOSP Android 17 把 `queueBuffer(ANativeWindowBuffer*, int, ...)` 改为 `queueBuffer(const sp<GraphicBuffer>&, const sp<Fence>&, ...)`。原依赖的两个符号都对应旧签名。本次保留旧符号优先，添加新签名的候选。BPF 只读取第一个参数作为 Surface 标识，因此不需要改变事件格式。候选符号已用 NDK C++ 编译器核对；OEM 符号导出与实际帧采样仍需真机验证。
- **16 KiB BPF ring buffer**：内置 BPF map 固定为 4096 字节；ring buffer 的容量须为内核页大小的 2 次幂倍数。在加载时按 `sysconf(_SC_PAGESIZE)` 覆盖容量，兼容 4/16/64 KiB 页，避免 16 KiB 内核上 map 创建失败。
- **ELF 对齐门禁**：CI 检查最终 ARM64 可执行文件的全部 `PT_LOAD` 段，要求至少 16 KiB 对齐且偏移/虚拟地址同余。ELF 对齐与 BPF map 容量是两个独立条件。

16 KiB 支持始于 Android 15；Android 17 新增可令不兼容二进制立即终止的 `fatal` 调试模式。这些改动是兼容性准备，并非已经完成 Android 17 真机性能认证。

来源：[Android 17 Surface.cpp](https://android.googlesource.com/platform/frameworks/native/+/refs/heads/android17-release/libs/gui/Surface.cpp)、[Linux BPF ring buffer](https://docs.kernel.org/bpf/ringbuf.html)、[Android 16 KiB 页大小指南](https://developer.android.com/guide/practices/page-sizes)。

## 下一步最值得使用的系统能力

| 优先级 | 能力 | 对当前项目的具体价值与边界 |
| --- | --- | --- |
| 高 | Thermal headroom 与阈值回调 | 当前 `thermal.rs` 逐次读取少数厂商温度节点，缺失节点时温度默认为 0。可补充系统 `AThermal_getThermalHeadroom`，并在 API 36+ 使用 `AThermal_registerThermalHeadroomListener`，把预测热余量加入节流依据，减少高频 sysfs 读取。该回调始于 Android 16，Android 17 可继续使用；不是 17 独有。 |
| 高 | 每显示器桌面窗口状态 | Android 17 支持 per-display desktop windowing。当前 `dump.contains("freeform")` 只是全文子串检测，而焦点收集也不能覆盖同一显示器所有可见游戏。建议按 display/task/window 可见性解析，保存真实 Android 17 dump 作为测试样本，再改调度选择逻辑。 |
| 中 | task profiles / cgroup 抽象 | `main.rs` 写死 `/dev/cpuset/background/cgroup.procs` 且忽略错误。可按设备探测 task profiles/libprocessgroup 入口，再回退原路径。该机制早于 Android 17，但适合应对新 ROM 的 cgroup 布局；不能假定所有 Android 17 设备都使用同一 cpuset 路径。 |
| 中 | ADPF Performance Hint / CPU-GPU headroom | 应优先由游戏进程或游戏内插件提供真实 workload 时长。Android 17 的 HintManagerService 检查调用者 UID/TID 所属关系；root 守护进程不能仅凭游戏 TID 就通过公开 API 替任意 UID 创建 session。采样到的 queueBuffer 间隔也不等于 CPU 实际工作时长。 |
| 低 | ProfilingManager 新触发器 | Android 17 新增冷启动、OOM、过度 CPU、异常 Binder/内存等触发器，适合将来配套 APK 的诊断。当前 Rust daemon 没有 Java Application/Context，不适合仅为此引入 JNI/管理 APK；先用 Perfetto 做对照评测更直接。 |

热余量接入建议：通过动态符号探测启用新接口，旧系统和不支持的设备回退 sysfs；保留用户的 `core_temp_thresh = "disabled"` 语义；headroom 返回 NaN 或 Binder 服务不可用时不当作“低温”。轮询频率遵守官方限制，回调仅更新缓存，控制线程读取缓存。需要用持续游戏场景比较卡顿分布、功耗、温度及守护进程开销，再决定默认策略。

官方来源：[Thermal NDK API](https://developer.android.com/ndk/reference/group/thermal)、[ADPF Thermal](https://developer.android.com/games/optimize/adpf/thermal)、[Android 17 系统更新](https://source.android.com/docs/whatsnew/android-17-release)、[task profiles/cgroups](https://source.android.com/docs/core/perf/cgroups)、[Android 17 HintManagerService](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android17-release/services/core/java/com/android/server/power/hint/HintManagerService.java)、[Android 17 新 API](https://developer.android.com/about/versions/17/features)。
